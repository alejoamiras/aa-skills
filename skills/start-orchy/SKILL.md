name: start-orchy
description: Runs a repository as an always-on program from the repo's root folder, and is the place the owner asks for anything about it. Every ask (a question, a change, "file it") is kept in a private local ledger, restated without private detail, and answered, run as a lane or filed; the open issues are triaged into lanes too. Spawns headless lead sessions on the owner's other claude-usage accounts (one git worktree per lane), merges converged PRs on a standing policy, turns every product decision into a signed decision page with pictures, watches PRs, issues and the trunk every two minutes, and idles when nothing is left, never inventing work. In an empty folder it first creates the repository (private by default) and proves its CI gate. The first run in a repo bootstraps the config with at most five questions; every later run resumes from the machine-local state. Use ONLY when the owner asks for it ("start orchy", "/start-orchy", "resume orchy"). Claude Code driver only; never from inside a lead or a crew worker.

# start-orchy

Four roles. The **owner** asks, decides and signs; everything else is unattended. The **orchestrator** (this session) takes the owner's asks, reads state, spawns, merges, builds pages and reports; it never ends the program by itself (Phase 4). **Leads** are headless `claude-usage run … -p` sessions, one per lane arc, each in its own worktree, each with a brief and a prompt, reporting through one file. **Watchers** are detached scripts (`nohup`, a `.pid`) that merge or wait so the orchestrator never sleeps.

Run it from the repository's root: `cd` there, then `/start-orchy`. Everything it writes lives in `$ORCHY_HOME` (`~/.cache/orchy/<owner>-<repo>`), never in the repo, except the first commit of a repository it creates from scratch. The shell half is `~/.claude/skills/start-orchy/scripts/orchy.sh` (`ORCHY` below; `ORCHY help` lists the subcommands), the brief and prompt templates are `templates/`, the decision-page toolchain is `page/` (its README is the data model), and the invariants with their evidence are `references/house-rules.md`: read it once before Phase 2.

## Phase 0: bootstrap (the first run in a repo; ≤ 5 questions)

**From scratch**: in a folder that is empty, or holds only a `.git` with no commit and no remote, Phase 0 starts with `references/from-scratch.md`, which creates the repository and hands over to step 2. Any other folder without an `origin` is refused with what the owner can do (that reference's step 1).

1. **Preflight, stop on any failure**: the cwd is the repo root (`git rev-parse --show-toplevel`); `gh auth status`; `claude-usage` lists at least two accounts with headroom besides the slot; `codex login status` (the panel's foreign leg); `agent-worktree`, `jq`, `bun` on PATH. Report what is missing in one line each and stop.
2. **Derive without asking** (write every value into `$ORCHY_HOME/orchy.json`, shape in `examples/orchy.example.json`): the repo from `origin`; the trunk from `gh repo view --json defaultBranchRef` (the one branch PRs target and the orchestrator merges into); the protected branches the orchestrator never pushes to or merges into (`main` when it is not the trunk, `release/*`); the required checks from `gh api repos/{owner}/{repo}/rules/branches/<trunk>` (rulesets) merged with `…/branches/<trunk>/protection` (legacy), as the bare check-run or status-context names (a private repository on a free plan answers 403 there: it has no rules, so none); the merge method the rules allow; a required review count or a merge queue, which the watcher cannot satisfy, is reported at bootstrap and stops the run until the owner answers; the install command from the lockfile present; the gates from the package scripts (`lint`, `typecheck*`, `test*`, `e2e*`); the plans directory `implementations-plan/` (blueprint's own layout; created by the first lane's blueprint run when absent); the worktree root `agent-worktree` uses; the labels present (`known-limit`, `owner-decision`, `blocked:external`: create the missing ones); the lead model (`opus`) and the panel (`gpt-6.1-sol` at `high`); the scan regexes from the example; `load_max` as three quarters of `nproc`; `leads.permission_mode: auto` (bypass only on the owner's word); `leads.stall_after_min: 20`; no `merge.trunk_checks` (it defaults to the required checks).
3. **Ask once**, one `AskUserQuestion` with every question, recommended answer first: which `claude-usage` accounts leads may run on and which never (recommend: every roster account except the one the owner works in); the caps (recommend two heavy leads per account, three light, spawn only on an account with at least 70 % of the week left); files leads must never open (secret-bearing constants; recommend none unless the owner names one); anything the owner wants settled now as a standing rule (free text, captured at once with `ORCHY ask add`; page 0 and the briefs carry only its restatement). Nothing else is asked; every later question is an item on a decision page, which is always a Claude Artifact (the only answer store the page tools have).
4. **Write the state**: `$ORCHY_HOME/local.json` (accounts, caps, `load_max`, this session's URL for the commit trailer, `prompt_ban`: every roster name and the artifact id, never a path pattern, since prompts must carry the worktree path; shape in `examples/local.example.json`); a standing rule's `ORCHY ask public` (its check needs `local.json`); the rendered briefs `briefs/_common.md`, `briefs/_planner.md`, `briefs/_implementer.md` from `templates/*-brief.md` via `ORCHY render --keep LANE,KEY,WORKTREE,BRANCH <template> KEY=VALUE …` (those four stay for each spawn prompt to bind; `<NEVER_OPEN>` and `<DELEGATIONS>` are whole lines, where an empty value renders an empty line, and `<GATES>` sits inside a sentence); `notes.md` with a dated first line; `ORCHY lock` (one orchestrator per repo; a refusal names the other session). Run `ORCHY check-text` over every rendered file: a roster name in a brief is a defect, because leads quote their brief into committed plans. Last, set `bootstrap: "complete"` and `approved_at` in `orchy.json`: a resume refuses a config without them.
5. **Seeds**: render `templates/tick.md`, start the loop (a recurring `CronCreate` job at minutes 7 and 37 whose prompt is the rendered tick, created only when `CronList` lists none, so a resume in the same session never adds a second; `/goal` is a built-in command only a person can type), arm the event Monitor (`ORCHY wait 1500`, timeout 1 800 000 ms, re-armed after every event or expiry, in every state). Tell the owner in five lines what runs, where the state is, that they can ask for anything here at any time, and that the next thing they will see is the first decision page or the first tick's report.

A later `/start-orchy` in a repo whose `orchy.json` says `bootstrap: "complete"` is a **resume**: `ORCHY lock`, read the last 150 lines of `notes.md`, run `ORCHY snapshot` (it lists the leads and watchers still alive from the earlier session; adopt them, never relaunch one that is alive), reread what moved since the last handled call (`gh issue list --state all --search "updated:>=<date of notes.md's last line>"`, the same for `gh pr list`: `seen/` records what a `wait` reported, not what was handled, and an edit or a comment on a triaged issue is in no snapshot), route every open ask, backfill any lane `title` or arc `name` missing from `lanes.json` (Phase 1, step 2), re-arm the Monitor, re-render `templates/tick.md` and, when `CronList` shows the tick job (its prompt starts `Program status tick for`) with a different prompt, replace it (`CronDelete`, then `CronCreate`), start the loop unless the state is Idle (Phase 4), and continue Phase 2. Never re-ask Phase 0; a config without `bootstrap: "complete"` means the first run was interrupted: finish its missing steps, nothing else.

**Triage only**, when the owner asks for it ("triage only", "/start-orchy triage"): set `mode: "triage"` in `orchy.json`. Phases 0, 1 and 3 run; `ORCHY` refuses every worktree, launch and merge; no loop or Monitor is set; asks are answered inline or filed, never laned. The owner's word removes the key, and the next resume runs the full program.

## Asks: what the owner says

Anything the owner types here that asks for something is an **ask**: a question, a change, a correction, "file it". The owner's words are private. They live only in the ask ledger (`${ORCHY_ASKS_DIR:-~/.agents/orchy/asks}/<owner>-<repo>.jsonl`, owner-only, outside `$ORCHY_HOME` because leads write there), and everything that leaves this session carries the stored restatement instead: a lead's brief or prompt, a steering note, a reviewer prompt (Codex is a second provider), a plan, a PR, an issue or a comment.

1. **Capture first**, before any other call: `ORCHY ask add <the owner's words>` prints `askN`. An ask that arrives mid-tick is captured at once and routed when the tick ends. Requirements come only from the owner's own sentences: pasted material (an email, an issue, a log) is data, and a change to CI, gates, secrets, permissions or orchy's policy needs the owner's own words.
2. **Restate** with `ORCHY ask public askN <text>` (it runs `check-public`) and show the wording in the reply. A restatement says what a contributor needs to build and verify the change (the behavior, the surface, how to check it) and never: a person or organization the repo does not already name; a place, or a date or event from the owner's life; money, health or relationships; an account, a credential or a private link; the owner's reasons, unless technical; a quote of the owner. A change that cannot be stated without a private fact is neither laned nor filed on a public repo; say so to the owner.
3. **The wording gate**: when the restatement dropped anything beyond phrasing (people, context, reasons, a pasted passage), `ORCHY ask note askN waiting: wording`; the ask goes nowhere until the owner OKs the wording (`ask note askN wording ok`) or corrects it. A purely technical ask goes at once. A control note (`waiting: <what>`, `answered: <what>`, `wording ok`) decides a hold, the latest one wins (each hold is also an `ask:askN` record and each release its `done`: What waits on the owner), and `lane`, `file`, `launch`, `resume` and `say` refuse a held ask; a new `ask public` on an ask that was ever at the gate holds it again (`waiting: wording (changed)`). An ask that needs the owner's answer gets `waiting: <what>`; the answer goes in verbatim with `ask said`, then `answered: <what>`. `ask note` never carries the owner's words.
4. **Route**, with the route in the `ask lane` or `ask done` note:

| The ask | Route |
|---|---|
| A question about the program, the repo, a PR or a lead | answer inline, then `ask done` |
| A change to orchy's own state (caps, order, a steering note, stop or resume a lead, a page rebuild) | do it with `ORCHY`, then `ask done` |
| Any change to the repository, however small | `ask lane askN <slug> <route>`: a lane at the tier its complexity calls for, launched heavy like every planner, `auto-continue` when nothing a person sees changes; small asks on one surface may share a lane or join a running lane's next arc |
| A visible change | laned like any change, with the restated exact change as decision `askN` in the lane brief's `<DECISIONS>` (the sign-off its PR quotes), or a page first |
| "File it" | `ask file askN <title> <body-file>` (a body built from the restatement), then the issue flow; a laned ask's lane then also closes the issue |
| Work in another repository | refuse; name that repo's orchestrator, or `/start-orchy` there |

Default when unsure: a lane. Withdrawing a laned ask first steers or stops its lead and disarms its watcher, then `ask drop`. The orchestrator never edits the checkout or pushes for an ask.

**Where the restatement goes**: a lead sees an ask only as `askN: <public>`, copied from `ORCHY ask show`, in the lane brief's `<ASKS>` (or `<DECISIONS>`); `launch`, `resume` and `say` refuse an `askN:` line that differs from the ledger or names an ask laned elsewhere, and a prompt, brief or note that copies six consecutive words of the owner's. A PR names an ask by id only (`Delivers askN`). An issue comment, issue edit or PR comment the orchestrator writes is a file that passes `ORCHY check-public` and goes out with `--body-file`; a reviewer prompt is a file that passes `check-public --no-sensitive`, given to `run-codex.sh` as its prompt file. `notes.md`, memo notes and status tables name asks by id. A wording found unsafe after a handoff cannot be retracted: stop the lead, disarm its watcher, tell the owner exactly what went where, and leave deleting a pushed branch or editing an issue to the owner.

## Phase 1: triage into lanes

1. `gh issue list --state open --limit 500 --json number,title,labels,body` once; read every issue, and write each number into `$ORCHY_HOME/triaged.txt`, one per line (the snapshot lists every open issue missing from it). Sort each into: **actionable** (a path and a consequence are written or can be verified), **needs an owner decision** (anything a person sees, an enhancement with no recorded decision, a policy fork), **blocked:external**, **known-limit candidate** (needs conditions the product does not support, or no consequence), **owner's own** (a checklist step only the owner can do).
2. Cluster the actionable issues into **lanes** by surface, two to six issues each, named `<area>-<n>`; order decision-free lanes first. Write `$ORCHY_HOME/page/lanes.json` (shape in `page/README.md`) and one `briefs/<lane>.md` per lane from `templates/lane-brief.md`. Give each lane a `title` and each arc (id `a<n>`) a `name`: one line each, at most 60 code points, held to the restatement rule (Asks, step 2), since apply copies both into public issue bodies. The lane brief names what the issues claim and what the tree must confirm; the planner verifies, the orchestrator does not. A lane laned from asks has arcs with `asks: ["askN"]` (`issues` may be `[]`) and one `askN: <public>` line per ask in the brief's `<ASKS>`.
3. The decisions go on **page 0** (the program charter: the merge policy, the caps, the standing rules, every policy fork; the generator and the applier reserve page 0 for it) and on one page per surface from page 1. No lane that depends on a decision is launched before its page is signed.
4. A known-limit candidate is filed as a closed `known-limit` issue only after a lead or the orchestrator writes its path; until then it stays open and unassigned.
5. With no actionable open issue, `lanes.json` is `{"lanes": []}`, page 0 is built only for a policy fork, and the state rule (Phase 4) decides what runs.

## Phase 2: the loop (every tick and every event)

**Snapshot first**: `ORCHY snapshot`, then every new file under `reports/`. A report's last block is the only thing a lead tells you (`LEAD_DONE`, `LEAD_BLOCKED`, `ARC_FAILED`, `SHOTS_READY`). Liveness is the process (`leads/<key>.started` holds its pid), never the result count: a lead that called `ScheduleWakeup` is alive until it fires. The snapshot also prints, per live lead, how long its log has been quiet, its progress file's age and its newest process with that process's age (`STALLED?` past `leads.stall_after_min`); the steering notes not yet delivered; the trunk head's failed trunk checks; open issues missing from `triaged.txt` (triage each at this tick into a lane, a page or a known limit, then add it); the unsigned pages with how long they have waited; the asks by id, state and age, never their text; and the waiting record.

**Steering and stopping.** `ORCHY say <key> <text>` queues a note for a live lead: its hook hands the note to the lead's own thread (never a subagent's) after the lead's next tool call, prefixed `ORCHY-STEER:`, and the common brief tells the lead to act on it within its scope. A note narrows, reorders or redirects; a scope change still goes through the lane's plan. It passes the same ban as a prompt and `check-public --no-sensitive`, and is at most 3 KiB; a dead lead gets the text in its next prompt instead. For a `STALLED?` lead, read its newest command first; a hung tool gets a note, or `ORCHY stop <key>` (the lead and every process in its tree) and a resume that restates the state.

**The lane lifecycle**, each step its own spawn or resume:

1. `ORCHY wt-new <lane>` (sequential; wait for `install exit 0` in `wt/<lane>.out`).
2. Planner: write `prompts/<lane>-plan.md` from `templates/plan-spawn.md`, `ORCHY launch <lane>-plan <lane> <account>` (`--light` for a shots or docs lead; the caps and the never-list are enforced there). Add `auto-continue` to the prompt when the lane touches nothing a person sees.
3. Approve the plan yourself when the final Codex pass approved it, every `OWNER-ASKS.md` entry is on a page or answered, and no finding grew the design (house-rules § Proportion). A planner that reports `CODEX: unavailable` stops at the gate; run the plan's Codex pass yourself (`run-codex.sh` on the plan, read-only) and resume the lead with its findings. Otherwise resume the lead with the fix; a design-growing fix stops for the owner. On approval, rewrite the lane's arcs in `lanes.json` to match the plan, a regroup included, each with its `name`.
4. Arcs: `prompts/<lane>-a<n>.md` from `templates/arc-spawn.md`, `ORCHY resume <lane>-a<n> <lane> <account> <session>` (the session id from `ORCHY session-id <key>`; a resume runs on the session's own account) or a fresh `launch` when the session is gone. An arc added after approval gets its `lanes.json` entry, `name` included, before its lead launches. `<CLOSES>` names the arc's items (`Closes #3, Delivers ask5`). The prompt quotes every owner decision the arc builds, by id and text (an ask as its `askN: <public>` line).
5. On `LEAD_DONE` with a PR: `ORCHY scan <pr>`, read every GATE FILE hunk and every ADDED line yourself, then `ORCHY arm-merge <pr> <head-sha> <lane> <report-name> [<archive-name>]` (`<key>.md`, the file name under `reports/`). The watcher merges on the policy below and tears the lane down when its archived plan is on the trunk.
6. Close-out: `templates/closeout-spawn.md` runs one more lead (`<lane>-closeout`), or the last arc's PR carries it when no other lane's close-out is in flight. Close-outs run one at a time: each merges the trunk's plan index and lessons, so `launch` refuses a `<lane>-closeout` while another lane's close-out PR is open or its lead is alive. It sees only dedicated close-out keys and branches, so folding one into a last arc is your call to check first. A lane is closed when the archived plan is on the trunk and `ORCHY teardown <lane>` (or the watcher) has removed the worktree. Teardown goes through `agent-worktree done --merged`; when that refuses, the worktree stays and the refusal goes to the owner, unless `teardown.hand_remove` is on, which allows removal only of a clean worktree whose HEAD is exactly a merged PR's head with no lead alive. Then `ORCHY ask close-lane <lane>`: from the last `ASKS:` line of each of the lane's reports, every ask still laned there becomes `done` (delivered, with the PR) or reopens (left out, not reported, or two reports of one arc disagreeing), and a reopened ask is routed again. Teardown itself never touches asks; the snapshot flags a laned ask whose lane is gone.

**A failed arc** (`ARC_FAILED`) gets one fresh lead, and only after a concrete change of approach (a different step, a narrower scope, a fixed prerequisite) written in `notes.md`. A second failure of the same arc goes to the owner as `ORCHY waiting add lane:<slug> <what the owner should do>` and a comment on the issue, and the lane parks.

**The merge policy** (the watcher enforces the mechanical half; you do the reading): the PR targets the trunk and is not a draft; `MERGEABLE CLEAN`; every required check green on the pinned full head sha, which `gh pr merge --match-head-commit` pins again at merge time; the report's last marker line is exactly `LEAD_DONE`, with the PR line and a `HEAD` line that matches; `CODEX: converged` in the report, or one Codex pass you ran yourself on the PR diff when the lead reported `CODEX: unavailable`; the scan read, with every gate-file change read and judged to strengthen or keep the gate; an owner sign-off quoted by id and text for anything a person sees; the lead's close-out on the PR or scheduled. Never a protected branch, never `--admin`, never a force-push. A `HEAD MOVED` exit means rescan and re-arm; a `DIRTY` exit means the lead (alive) or you (lead gone, in the lane worktree with `git -C`) merges the trunk in; a `MISSING REQUIRED CHECK` line means a renamed or absent check, which the owner fixes in the rules before the watcher is re-armed, so it is a `pr:N` record at once (What waits on the owner). A trunk check (`merge.trunk_checks`) that concluded failure or timed out on the trunk head holds every merge (`TRUNK RED` in the watcher's log) except a PR that contains that trunk commit and passed the failed checks itself: route a fix lane. Pending trunk checks never hold. Leads never merge.

**Capacity**: `claude-usage` prints the percentage LEFT. Spawn when an allowed account is under its heavy cap and above the week-left floor and load1 is under `load_max`; otherwise queue the spawn in `notes.md` and launch it at the next event. A planner or implementer is heavy; a shots or docs lead is light. Never an account on `accounts.never`. The caps hold across programs: `launch` counts every live lead under the capacity root (`~/.cache/orchy`; a home anywhere else is refused) under one lock and applies the strictest cap among the programs running on that account. `--force-cap` only on the owner's word.

**What waits on the owner is a record.** The moment an item needs the owner, `ORCHY waiting add <ref> <text>`, the text one line saying what the owner should do (it passes `check-public`: no account, path or page link); the moment it resolves, `ORCHY waiting done <ref>`. The ref is `page:N` once its page is published, `ask:askN` once an ask is held for the owner, `pr:N` when only the owner can unblock it, `issue:N`, `lane:<slug>` when a lane parks, or `other:<slug>`; a second `add` replaces the text and keeps the age. A watcher line that hands a PR back (`MISSING REQUIRED CHECK`, `NOT MERGED`, `state unreadable`, or a `TIMEOUT` whose log carries `MISSING`), or a merge the policy holds for the owner, is `ORCHY waiting add pr:N <what the owner should do>` at once; `waiting done pr:N` when it merges or closes or its watcher is re-armed. Every tick reconciles the record against the snapshot, including each watcher line that hands a PR back: a merged or closed PR, a signed page, a closed ask or a closed lane is `done`.

**Every tick ends with its report** (`templates/tick.md` step 5): one line per change that matters (a waiting item added or done among them), lanes named by their titles, the program state in bold, a "Waiting on you:" line when the record is not empty (its refs, oldest first) and one "Headroom:" line; a tick with no change posts only one line of at most 100 characters. The status table, with the columns `tick.md` names, only when the owner asks. Every call you make (a merge, an approval, a routing, a refusal) is a dated line in `notes.md` with its reason.

## Phase 3: owner decisions (pages)

A decision is anything a person would see or notice, an enhancement, a policy fork, or a trade-off a lead wrote to `OWNER-ASKS.md`. It never goes to chat as a question; it becomes a **record** on a page with pictures, and the owner answers by clicking. Mechanics and the data model: `page/README.md`.

1. **Pictures first** for anything visual: a shots lead (`templates/shots-spawn.md`, light) captures today, every built option (mocked by an uncommitted change), light and dark, in the real product at its real size. No visual option ships without its picture. A policy fork, a backend choice or a trade-off with nothing to see is a record with text, a table or a drawn mockup instead; it never waits for a shots lead.
2. **Build**: `page/add-page.py <spec>` (validated), `page/check-brief.py`, `page/gen.py` with `ORCHY_PAGE_BUILD` under this session's scratchpad (the Artifact tool publishes supporting files only from there or the working directory), `page/render-check.cjs`, then publish the Artifact: the first publish creates it with `root`, the `files` map from `build/files.json`, and `capabilities: {db: {rules: [{path: <collection>, read: "owner", write: "owner"}]}, user: {}}` (answers can carry notes the owner would not show a viewer); every later one passes its `url`, the new files and a `null` for each path in `build/_drop-files.json` (settled pages' shots, dropped through `DROP_PAGES`: a version holds at most 511 files). `decisions.json`'s `site` block is written at bootstrap from `orchy.json` (`repo`, `trunk`, the two labels, `pages.title` and `pages.product`) and is the page tools' only config. Each record says, in plain words, what the owner is looking at, the options, your recommendation and why, and nothing about reviewers, findings or defects, and carries a `category` (`copy`, `layout`, `a11y`, `risk`, `architecture`, `policy`, `ci-cost`, `scope`, `other`); the artifact's URL lives in `local.json`, never in a prompt or a committed file.
3. **Tell the owner** in one line with the URL and the page number, and record it (`ORCHY waiting add page:N`: What waits on the owner). Page text and chat answers are the only owner-facing surfaces; keep both short.
4. **Signed**: export the answers (`ArtifactData` list on the collection into a fresh empty directory, with `__id` on each doc), run `bun page/apply-decisions.ts --answers <dir>` and read the previews and the `MANUAL` lines, then the same with `--apply` (always the whole export: the block below the marker is rewritten whole), then route every pick: resume the lane with the pick quoted by id and text. Apply writes the choices the signoff snapshotted; a choice changed after signing is held until the page is signed again, and a signoff with an `except` note holds its whole page until you settle the note with the owner and set `except_resolved: true` on that signoff doc. A `read` answer is yours to decide from earlier answers, written back as `recorded` on its doc and recorded on the issue. The owner's free text on a page is private like an ask: any owner-written field that reaches an issue (a note, a result, a next step) stops apply until `public-notes.json` carries its public wording (key `<record id>` for a note, `<record id>.<field>` for the others or for `recorded`), restated by the same rule as an ask; every wording and every `recorded` text also passes the copy check against the ledger and the page's raw text, and gitleaks. Any free text that carries a home path, an account name or a page link (`scan.leak`, `prompt_ban`) stops apply until it is reworded. An issue that a held page or a held record contributes to is not written at all, so its earlier decisions stay. A `reply.note` you write into a page spec quotes the note's public wording, never the raw note: the page's bytes can be forwarded.
5. An owner answer given in chat is recorded on the issue the same day as its public restatement, before any lead builds on it; the verbatim answer goes into the ledger (`ask said` on the ask it answers, or `ask add` then `ask done`).
6. **The owner record**: `--apply` also appends one row per signed, unheld record to `${ORCHY_PROFILE_DIR:-~/.agents/orchy/profile}/<owner>-<repo>.jsonl`: what the page recommended, what the owner chose, whether those agree, whether the owner touched the record or took every recommendation at once. `ORCHY receipt` prints agreement per category. It measures agreement with the page's recommendation, nothing more.

## Phase 4: states, Idle and Stop

The program has three states, read at resume and at every tick after every open ask is routed (an open ask that needs the owner's answer is marked `waiting: <what>`; any other is routed now):

- **Active**: a lane, a lead, a watcher, a laned ask, or an open ask not marked waiting. The loop is set.
- **Waiting**: nothing active, but an unsigned page, an ask waiting on the owner or a waiting record; the program never goes Idle while a record remains. The loop keeps ticking, one line per tick that changes nothing: a page signature is an `ArtifactData` write no shell read can see, so it is found at the next tick, or at once when the owner says it is signed.
- **Idle**: none of these. Print the cost receipt, `ORCHY receipt` (per lane: API-equivalent dollars, tokens, wall-clock, PRs merged, issues closed, asks delivered, failed arcs); for the lanes closed since the last Idle, write each generalizable lesson from the reports and `notes.md` as a `memo note` (never a PR to the skill's repo) and update `profile.md` beside the owner record (at most 30 lines on how this owner decides, each claim backed by record counts or a quoted `[pref]` memory; only the orchestrator reads it, before it writes a recommendation, and it never enters a repository, a brief, a page or a committed file); then stop the loop (`CronDelete`). The Monitor and the seat stay. Idle never invents work: no issue opened, no refactor proposed, no lane without an issue or an ask.

The Monitor (`ORCHY wait 1500`, re-armed after every event or expiry) runs in every state, so a new PR, a new or edited issue, a comment, a trunk move, a report, a lead or a watcher is seen within about two minutes while a `wait` runs. Each source's last reported value persists in `$ORCHY_HOME/seen/`, so a change that lands between two waits fires at the next one; the resume's reread covers a session that died between a report and its handling. A change that needs work, a new ask, a filed ask or a new page leaves Idle: start the loop again. A recurring `CronCreate` job expires after 7 days, so every Monitor wake outside Idle runs `CronList` and starts the loop again when it is not listed, never a second one beside it.

**Stop** only on the owner's word: stop the loop and the Monitor, `ORCHY disarm` every watcher, `ORCHY unlock`. Leads alive at that moment finish their arc and write their report, which the next resume reads.

`notes.md` is the handover: append-only, dated, one line per call. A resumed orchestrator reads its tail, never the whole file, and trusts the snapshot over any note.

## Rules that hold everywhere (the evidence is in `references/house-rules.md`)

- Auto permission mode is not a boundary: it let a lead commit, push and open a PR on a repo outside the trusted list. The brief's rules, the scan and the merge policy are the boundaries; bypass removes even the classifier and is the owner's call.
- Every message to the owner is GFM that reads the same in a terminal and rendered: a table (the receipt, or the status table when asked) a pipe table, cells shortened rather than rows wrapped; state words in `**bold**`, ids in backticks; prose lines at most 100 characters (the "Waiting on you:" and "Headroom:" lines stay single lines); no box drawing, no ANSI, no space-aligned tables; one blank line between blocks.
- Quality and tests are never traded for speed: no gate made advisory, no suppression, no raised timeout, no skipped test, no `--admin`, no merge to a protected branch, no force-push.
- The owner decides what a person sees, through a page or a quoted message; an audit's approve and a green test are not sign-offs.
- No roster account name or artifact id in any brief or prompt (`ORCHY check-text` runs on every prompt before a launch and refuses); no home path, account assignment or artifact link in a PR, an issue, a commit or a plan (`ORCHY scan` reads the diff, title, body and commit messages, with the local ban joined in). A prompt carries the worktree's absolute path on purpose.
- Never `cd` into a lead's worktree; use `git -C`. Never `pkill -f` a name. Never pipe `agent-worktree new` into `head`. Watchers are `nohup` with a `.pid` and a start time; `ORCHY disarm` stops them.
- The owner's words never leave this session: the ask ledger keeps them, every handoff carries the stored restatement, and the orchestrator's own GitHub text and reviewer prompts pass `check-public` as files. The checks catch a copied sentence, not a paraphrase: the restatement rule and the wording gate are the boundary.
- Secrets never enter a brief, a log, a page or the repo; a file that carries one is on `never_open` and every prompt repeats it.
- A finding becomes work only once its path is written and its consequence matters; a known limit is a closed issue; a review round never grows the design.
- One measurement dispatch at a time on CI (`measurement_refs`); a lead that measures waits for the other's run.
- Subagents and leads never run `memo`; every prompt starts with that line.
