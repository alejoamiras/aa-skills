---
name: start-orchy
description: Runs a repository's whole backlog as an unattended program from the repo's root folder. Triages the open issues into lanes, spawns headless lead sessions on the owner's other claude-usage accounts (one git worktree per lane), merges converged PRs on a standing policy, turns every product decision into a signed decision page with pictures, and ticks every 35 minutes until the backlog is done. The first run in a repo bootstraps the config with at most five questions; every later run resumes from the machine-local state. Use ONLY when the owner asks for it ("start orchy", "/start-orchy", "resume orchy"). Claude Code driver only; never from inside a lead or a crew worker.
---

# start-orchy

Four roles. The **owner** decides and signs; everything else is unattended. The **orchestrator** (this session) reads state, spawns, merges, builds pages and reports. **Leads** are headless `claude-usage run … -p` sessions, one per lane arc, each in its own worktree, each with a brief and a prompt, reporting through one file. **Watchers** are detached scripts (`nohup`, a `.pid`) that merge or wait so the orchestrator never sleeps.

Run it from the repository's root: `cd` there, then `/start-orchy`. Everything it writes lives in `$ORCHY_HOME` (`~/.cache/orchy/<owner>-<repo>`), never in the repo. The shell half is `~/.claude/skills/start-orchy/scripts/orchy.sh` (`ORCHY` below; `ORCHY help` lists the subcommands), the brief and prompt templates are `templates/`, the decision-page toolchain is `page/` (its README is the data model), and the invariants with their evidence are `references/house-rules.md`: read it once before Phase 2.

## Phase 0: bootstrap (the first run in a repo; ≤ 5 questions)

1. **Preflight, stop on any failure**: the cwd is the repo root (`git rev-parse --show-toplevel`); `gh auth status`; `claude-usage` lists at least two accounts with headroom besides the slot; `codex login status` (the panel's foreign leg); `agent-worktree`, `jq`, `bun` on PATH. Report what is missing in one line each and stop.
2. **Derive without asking** (write every value into `$ORCHY_HOME/orchy.json`, shape in `examples/orchy.example.json`): the repo from `origin`; the trunk from `gh repo view --json defaultBranchRef` (the one branch PRs target and the orchestrator merges into); the protected branches the orchestrator never pushes to or merges into (`main` when it is not the trunk, `release/*`); the required checks from `gh api repos/{owner}/{repo}/rules/branches/<trunk>` (rulesets) merged with `…/branches/<trunk>/protection` (legacy), as the bare check-run or status-context names; the merge method the rules allow; a required review count or a merge queue, which the watcher cannot satisfy, is reported at bootstrap and stops the run until the owner answers; the install command from the lockfile present; the gates from the package scripts (`lint`, `typecheck*`, `test*`, `e2e*`); the plans directory `implementations-plan/` (blueprint's own layout; created by the first lane's blueprint run when absent); the worktree root `agent-worktree` uses; the labels present (`known-limit`, `owner-decision`, `blocked:external`: create the missing ones); the lead model (`opus`) and the panel (`gpt-6.1-sol` at `high`); the scan regexes from the example; `load_max` as three quarters of `nproc`; `leads.permission_mode: auto` (bypass only on the owner's word); `leads.stall_after_min: 20`; no `merge.trunk_checks` (it defaults to the required checks).
3. **Ask once**, one `AskUserQuestion` with every question, recommended answer first: which `claude-usage` accounts leads may run on and which never (recommend: every roster account except the one the owner works in); the caps (recommend two heavy leads per account, three light, spawn only on an account with at least 70 % of the week left); files leads must never open (secret-bearing constants; recommend none unless the owner names one); anything the owner wants settled now as a standing rule (free text). Nothing else is asked; every later question is an item on a decision page, which is always a Claude Artifact (the only answer store the page tools have).
4. **Write the state**: `$ORCHY_HOME/local.json` (accounts, caps, `load_max`, this session's URL for the commit trailer, `prompt_ban`: every roster name and the artifact id, never a path pattern, since prompts must carry the worktree path; shape in `examples/local.example.json`); the rendered briefs `briefs/_common.md`, `briefs/_planner.md`, `briefs/_implementer.md` from `templates/*-brief.md` via `ORCHY render <template> KEY=VALUE …` (`<GATES>`, `<NEVER_OPEN>`, `<DELEGATIONS>` are whole lines; an empty value renders an empty line); `notes.md` with a dated first line; `ORCHY lock` (one orchestrator per repo; a refusal names the other session). Run `ORCHY check-text` over every rendered file: a roster name in a brief is a defect, because leads quote their brief into committed plans. Last, set `bootstrap: "complete"` and `approved_at` in `orchy.json`: a resume refuses a config without them.
5. **Seeds**: render `templates/goal.md` and `templates/tick.md`, set the goal with `/goal <text>` and the loop with `/loop 35m <text>`, arm the event Monitor (`ORCHY wait 1500`, timeout 1 800 000 ms, re-armed after every event or expiry). Tell the owner in five lines what runs, where the state is, and that the next thing they will see is the first decision page or the first status table.

A later `/start-orchy` in a repo whose `orchy.json` says `bootstrap: "complete"` is a **resume**: `ORCHY lock`, read the last 150 lines of `notes.md`, run `ORCHY snapshot` (it lists the leads and watchers still alive from the earlier session; adopt them, never relaunch one that is alive), re-arm the Monitor and the loop, and continue Phase 2. Never re-ask Phase 0; a config without `bootstrap: "complete"` means the first run was interrupted: finish its missing steps, nothing else.

**Triage only**, when the owner asks for it ("triage only", "/start-orchy triage"): set `mode: "triage"` in `orchy.json`. Phases 0, 1 and 3 run; `ORCHY` refuses every worktree, launch and merge; no goal, loop or Monitor is set. The owner's word removes the key, and the next resume runs the full program.

## Phase 1: triage into lanes

1. `gh issue list --state open --limit 500 --json number,title,labels,body` once; read every issue, and write each number into `$ORCHY_HOME/triaged.txt`, one per line (the snapshot lists every open issue missing from it). Sort each into: **actionable** (a path and a consequence are written or can be verified), **needs an owner decision** (anything a person sees, an enhancement with no recorded decision, a policy fork), **blocked:external**, **known-limit candidate** (needs conditions the product does not support, or no consequence), **owner's own** (a checklist step only the owner can do).
2. Cluster the actionable issues into **lanes** by surface, two to six issues each, named `<area>-<n>`; order decision-free lanes first. Write `$ORCHY_HOME/page/lanes.json` (shape in `page/README.md`) and one `briefs/<lane>.md` per lane from `templates/lane-brief.md`. The lane brief names what the issues claim and what the tree must confirm; the planner verifies, the orchestrator does not.
3. The decisions go on **page 0** (the program charter: the merge policy, the caps, the standing rules, every policy fork; the generator and the applier reserve page 0 for it) and on one page per surface from page 1. No lane that depends on a decision is launched before its page is signed.
4. A known-limit candidate is filed as a closed `known-limit` issue only after a lead or the orchestrator writes its path; until then it stays open and unassigned.

## Phase 2: the loop (every tick and every event)

**Snapshot first**: `ORCHY snapshot`, then every new file under `reports/`. A report's last block is the only thing a lead tells you (`LEAD_DONE`, `LEAD_BLOCKED`, `ARC_FAILED`, `SHOTS_READY`). Liveness is the process (`leads/<key>.started` holds its pid), never the result count: a lead that called `ScheduleWakeup` is alive until it fires. The snapshot also prints, per live lead, how long its log has been quiet, its progress file's age and its newest process with that process's age (`STALLED?` past `leads.stall_after_min`); the steering notes not yet delivered; the trunk head's failed trunk checks; open issues missing from `triaged.txt` (triage each at this tick into a lane, a page or a known limit, then add it); and the unsigned pages with how long they have waited.

**Steering and stopping.** `ORCHY say <key> <text>` queues a note for a live lead: its hook hands the note to the lead's own thread (never a subagent's) after the lead's next tool call, prefixed `ORCHY-STEER:`, and the common brief tells the lead to act on it within its scope. A note narrows, reorders or redirects; a scope change still goes through the lane's plan. It passes the same ban as a prompt and is at most 3 KiB; a dead lead gets the text in its next prompt instead. For a `STALLED?` lead, read its newest command first; a hung tool gets a note, or `ORCHY stop <key>` (the lead and every process in its tree) and a resume that restates the state.

**The lane lifecycle**, each step its own spawn or resume:

1. `ORCHY wt-new <lane>` (sequential; wait for `install exit 0` in `wt/<lane>.out`).
2. Planner: write `prompts/<lane>-plan.md` from `templates/plan-spawn.md`, `ORCHY launch <lane>-plan <lane> <account>` (`--light` for a shots or docs lead; the caps and the never-list are enforced there). Add `auto-continue` to the prompt when the lane touches nothing a person sees.
3. Approve the plan yourself when the final Codex pass approved it, every `OWNER-ASKS.md` entry is on a page or answered, and no finding grew the design (house-rules § Proportion). A planner that reports `CODEX: unavailable` stops at the gate; run the plan's Codex pass yourself (`run-codex.sh` on the plan, read-only) and resume the lead with its findings. Otherwise resume the lead with the fix; a design-growing fix stops for the owner.
4. Arcs: `prompts/<lane>-a<n>.md` from `templates/arc-spawn.md`, `ORCHY resume <lane>-a<n> <lane> <account> <session>` (the session id from `ORCHY session-id <key>`; a resume runs on the session's own account) or a fresh `launch` when the session is gone. The prompt quotes every owner decision the arc builds, by id and text.
5. On `LEAD_DONE` with a PR: `ORCHY scan <pr>`, read every GATE FILE hunk and every ADDED line yourself, then `ORCHY arm-merge <pr> <head-sha> <lane> <report> [<archive-name>]`. The watcher merges on the policy below and tears the lane down when its archived plan is on the trunk.
6. Close-out: `templates/closeout-spawn.md` runs one more lead (`<lane>-closeout`), or the last arc's PR carries it when no other lane's close-out is in flight. Close-outs run one at a time: each merges the trunk's plan index and lessons, so `launch` refuses a `<lane>-closeout` while another lane's close-out PR is open or its lead is alive. It sees only dedicated close-out keys and branches, so folding one into a last arc is your call to check first. A lane is closed when the archived plan is on the trunk and `ORCHY teardown <lane>` (or the watcher) has removed the worktree. Teardown goes through `agent-worktree done --merged`; when that refuses, the worktree stays and the refusal goes to the owner, unless `teardown.hand_remove` is on, which allows removal only of a clean worktree whose HEAD is exactly a merged PR's head with no lead alive.

**A failed arc** (`ARC_FAILED`) gets one fresh lead, and only after a concrete change of approach (a different step, a narrower scope, a fixed prerequisite) written in `notes.md`. A second failure of the same arc goes to the owner as a Waiting line and a comment on the issue, and the lane parks.

**The merge policy** (the watcher enforces the mechanical half; you do the reading): the PR targets the trunk and is not a draft; `MERGEABLE CLEAN`; every required check green on the pinned full head sha, which `gh pr merge --match-head-commit` pins again at merge time; the report's last marker line is exactly `LEAD_DONE`, with the PR line and a `HEAD` line that matches; `CODEX: converged` in the report, or one Codex pass you ran yourself on the PR diff when the lead reported `CODEX: unavailable`; the scan read, with every gate-file change read and judged to strengthen or keep the gate; an owner sign-off quoted by id and text for anything a person sees; the lead's close-out on the PR or scheduled. Never a protected branch, never `--admin`, never a force-push. A `HEAD MOVED` exit means rescan and re-arm; a `DIRTY` exit means the lead (alive) or you (lead gone, in the lane worktree with `git -C`) merges the trunk in; a `MISSING REQUIRED CHECK` line means a renamed or absent check, which the owner fixes in the rules before the watcher is re-armed. A trunk check (`merge.trunk_checks`) that concluded failure or timed out on the trunk head holds every merge (`TRUNK RED` in the watcher's log) except a PR that contains that trunk commit and passed the failed checks itself: route a fix lane. Pending trunk checks never hold. Leads never merge.

**Capacity**: `claude-usage` prints the percentage LEFT. Spawn when an allowed account is under its heavy cap and above the week-left floor and load1 is under `load_max`; otherwise queue the spawn in `notes.md` and launch it at the next event. A planner or implementer is heavy; a shots or docs lead is light. Never an account on `accounts.never`. The caps hold across programs: `launch` counts every live lead under the capacity root (`~/.cache/orchy`; a home anywhere else is refused) under one lock and applies the strictest cap among the programs running on that account. `--force-cap` only on the owner's word.

**Every tick ends with the status table** (`templates/tick.md` names the columns), then at most one "Waiting on you:" line and one "Headroom:" line. One line when nothing changed. Every call you make (a merge, an approval, a routing, a refusal) is a dated line in `notes.md` with its reason.

## Phase 3: owner decisions (pages)

A decision is anything a person would see or notice, an enhancement, a policy fork, or a trade-off a lead wrote to `OWNER-ASKS.md`. It never goes to chat as a question; it becomes a **record** on a page with pictures, and the owner answers by clicking. Mechanics and the data model: `page/README.md`.

1. **Pictures first** for anything visual: a shots lead (`templates/shots-spawn.md`, light) captures today, every built option (mocked by an uncommitted change), light and dark, in the real product at its real size. No visual option ships without its picture. A policy fork, a backend choice or a trade-off with nothing to see is a record with text, a table or a drawn mockup instead; it never waits for a shots lead.
2. **Build**: `page/add-page.py <spec>` (validated), `page/check-brief.py`, `page/gen.py` with `ORCHY_PAGE_BUILD` under this session's scratchpad (the Artifact tool publishes supporting files only from there or the working directory), `page/render-check.cjs`, then publish the Artifact: the first publish creates it with `root`, the `files` map from `build/files.json`, and `capabilities: {db: {rules: [{path: <collection>, read: "owner", write: "owner"}]}, user: {}}` (answers can carry notes the owner would not show a viewer); every later one passes its `url`, the new files and a `null` for each path in `build/_drop-files.json` (settled pages' shots, dropped through `DROP_PAGES`: a version holds at most 511 files). `decisions.json`'s `site` block is written at bootstrap from `orchy.json` (`repo`, `trunk`, the two labels, `pages.title` and `pages.product`) and is the page tools' only config. Each record says, in plain words, what the owner is looking at, the options, your recommendation and why, and nothing about reviewers, findings or defects, and carries a `category` (`copy`, `layout`, `a11y`, `risk`, `architecture`, `policy`, `ci-cost`, `scope`, `other`); the artifact's URL lives in `local.json`, never in a prompt or a committed file.
3. **Tell the owner** in one line with the URL and the page number. Page text and chat answers are the only owner-facing surfaces; keep both short.
4. **Signed**: export the answers (`ArtifactData` list on the collection into a fresh empty directory, with `__id` on each doc), run `bun page/apply-decisions.ts --answers <dir>` and read the previews and the `MANUAL` lines, then the same with `--apply` (always the whole export: the block below the marker is rewritten whole), then route every pick: resume the lane with the pick quoted by id and text. Apply writes the choices the signoff snapshotted; a choice changed after signing is held until the page is signed again, and a signoff with an `except` note holds its whole page until you settle the note with the owner and set `except_resolved: true` on that signoff doc. A `read` answer is yours to decide from earlier answers, written back as `recorded` on its doc and recorded on the issue with the quote. Any free text that names a reviewer or a finding stops apply until `public-notes.json` carries a public wording (key `<record id>` for a note, `<record id>.<field>` for a result, next step, recorded text or except note); an issue that a held page or a held record contributes to is not written at all, so its earlier decisions stay.
5. An owner answer given in chat is recorded on the issue the same day, quoted verbatim, before any lead builds on it.
6. **The owner record**: `--apply` also appends one row per signed, unheld record to `${ORCHY_PROFILE_DIR:-~/.agents/orchy/profile}/<owner>-<repo>.jsonl`: what the page recommended, what the owner chose, whether those agree, whether the owner touched the record or took every recommendation at once. `ORCHY receipt` prints agreement per category. It measures agreement with the page's recommendation, nothing more.

## Phase 4: done and handover

**Waiting** when every open issue is `blocked:external`, the owner's own, or an item on an unsigned page, and no lane is open: keep the loop, say so in one line per tick, and act the moment a page is signed. **Done** when nothing is on an unsigned page either: say so in the status table with `ORCHY receipt` (per lane: API-equivalent dollars, tokens, wall-clock, PRs merged, issues closed, failed arcs), stop the loop (`ScheduleWakeup stop` / `CronDelete`), `ORCHY disarm` any watcher still waiting, `ORCHY unlock`. Then write each generalizable lesson from the reports and `notes.md` as a `memo note` (never a PR to the skill's repo), and update `profile.md` beside the owner record: at most 30 lines on how this owner decides, each claim backed by record counts or a quoted `[pref]` memory. Only the orchestrator reads it, before it writes a recommendation; it never enters a repository, a brief, a page or a committed file. A stop the owner asks for mid-program is the same three commands; leads alive at that moment finish their arc and write their report, which the next resume reads.

`notes.md` is the handover: append-only, dated, one line per call. A resumed orchestrator reads its tail, never the whole file, and trusts the snapshot over any note.

## Rules that hold everywhere (the evidence is in `references/house-rules.md`)

- Auto permission mode is not a boundary: it let a lead commit, push and open a PR on a repo outside the trusted list. The brief's rules, the scan and the merge policy are the boundaries; bypass removes even the classifier and is the owner's call.
- Quality and tests are never traded for speed: no gate made advisory, no suppression, no raised timeout, no skipped test, no `--admin`, no merge to a protected branch, no force-push.
- The owner decides what a person sees, through a page or a quoted message; an audit's approve and a green test are not sign-offs.
- No roster account name or artifact id in any brief or prompt (`ORCHY check-text` runs on every prompt before a launch and refuses); no home path, account assignment or artifact link in a PR, an issue, a commit or a plan (`ORCHY scan` reads the diff, title, body and commit messages, with the local ban joined in). A prompt carries the worktree's absolute path on purpose.
- Never `cd` into a lead's worktree; use `git -C`. Never `pkill -f` a name. Never pipe `agent-worktree new` into `head`. Watchers are `nohup` with a `.pid` and a start time; `ORCHY disarm` stops them.
- Secrets never enter a brief, a log, a page or the repo; a file that carries one is on `never_open` and every prompt repeats it.
- A finding becomes work only once its path is written and its consequence matters; a known limit is a closed issue; a review round never grows the design.
- One measurement dispatch at a time on CI (`measurement_refs`); a lead that measures waits for the other's run.
- Subagents and leads never run `memo`; every prompt starts with that line.
