blueprint-remote-view

When a plan is created on the headless server, the "here's your plan, please approve it" page (eli5.html) used to be reachable only from the server itself. This adds one trick to the blueprint skill: if the machine provides a helper, the skill asks it for a web link when presenting a plan for approval — and tells it to take the link down as soon as you've given your verdict. On the server, the helper uses Tailscale (your private device network); on your Mac, nothing changes.

Approval record

Conditionally approved by Alejo, 2026-07-06, all three security questions answered: Tailscale network is owner-only ✓ · serving each repo's whole plans folder is deliberate ✓ · Tailscale operator grant OK ✓. Condition (now part of the design): links exist only while a plan awaits approval — the skill takes serving down right after the verdict, so shares never pile up.

Why this tier was chosen

light — rubric: novelty LOW (mechanism hand-proven the same day), blast radius LOW (worst case: a plan page doesn't load), irreversibility LOW (git revert + one off-command), migration NONE, external coupling MODERATE (Tailscale CLI), security LOW-MODERATE (private-network-only, plan docs only, now time-bounded). Zero HIGH → lightest tier, single codex audit. Codex: conditional approve, conditions folded in.

Phases

Phase 1: Teach the skill the trick (docs only)

New rule in the skill: helper configured → get a link, show it; verdict recorded → tell the helper to take it down; anything fails → today's behavior, announced out loud, never silent.

Proves itself by: contract text present in both doc files + no script accidentally broken.

Phase 2: Build the helper

A small careful script with an "up" and a "down" mode. Up: shares ONLY implementations-plan folders, refuses anything outside Projects, refuses trick-links (symlinks) pointing elsewhere. Down: removes exactly that share, and is happy being called on something already down.

Proves itself by: shell linter green + five refusal/idempotency tests behaving exactly as specified.

Phase 3: Plug it in on the server

A symlink and an environment variable so Claude Code sessions find the helper — plus a truth learned during testing: Tailscale insists on root for serving files (its lighter "operator" permission only covers status and port-forwarding). So the helper uses passwordless sudo, which this server already grants; on any other machine that's a real trust decision the script's header calls out.

Proves itself by: share status readable without sudo + the variable visible inside a real Claude Code session.

Phase 4: Prove the full life cycle, across repos

Share plans from two different repos at once, check both load from the tailnet, run "up" twice (nothing duplicates), take one down (the other keeps working), take both down (nothing left serving).

Proves itself by: 200s while up, refusals after down, zero leftover shares at the end — plus you opening the link on your Mac.

Phase 5: Ship

Code review pass, codex post-implementation audit, clean conventional commits, push to the private repo (your Mac inherits the skill change on next pull — where it's inert, because the Mac sets no helper).

Proves itself by: clean git tree after push + secret-scanning CI green.

Human context

The design's one big idea: the skill knows an interface ("a command that turns a plan folder into a link, and back off again"), never a technology. Tailscale, the port number, and this server's name live only inside the example helper. A future cloud box implements the same two-verb contract with whatever it has. Codex pushed on trick-links, leftover shares, and "who else can see this?" — all absorbed. Your approval added the best constraint: shares are approval-window-only, which turned codex's "stale mounts" worry from a documented caveat into a non-problem by design.
